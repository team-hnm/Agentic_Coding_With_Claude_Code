# 6. 메모리와 대화 세션 관리

## 학습 목표
- 클로드 코드의 메모리와 메모리 시스템

---

## 메모리 시스템
AI가 자율적으로 코드를 탐색하고 수정하려면 프로젝트의 규칙과 개발자의 선호도를 지속적으로 참조해야 한다.
따라서 클로드 코드는 세션 간에 기본 설정을 기억하는 계층적 메모리 시스템을 제공한다.

메모리 시스템은 개발자의 작업 맥락을 이해하고 일관된 응답을 제공하기 위한 지식 저장소 역할을 하며 이 시스템의 핵심은 `CLAUDE.md`파일이다.

### 메모리 시스템의 네 가지 계층
1. 관리형 계층 : 조직 전체에 적용. 조직의 모든 사용자에게 공유되며 보안 정책이나 코드 표준과 같은 전사적 규칙을 정의
2. 프로젝트 메모리: 팀에 공유. 프로젝트별 코딩 스타일, 아키텍쳐 결정, 빌드 명렁어 등을 문서화하는데 적합, 세션 시작 시가 아니라 해당 디렉터리의 파일을 읽을 때 온디맨드로 로딩
3. 사용자 메모리: 개인의 모든 프로젝트에 적용되는 기본 설정
4. 프로젝트 로컬 메모리: 현재 프로젝트에 대한 개인적인 기본 설정

> 온디맨드?
> 
> 작업 디렉터리 **상위** 경로의 CLAUDE.md는 launch 시점에 전체가 로드된다. 온디맨드 로딩은 작업 디렉터리 **하위**(subdirectory)의 CLAUDE.md에만 적용되며, 그 하위 디렉터리 파일을 실제로 읽을 때 로드된다.

> 우선순위: 프로젝트 로컬 메모리 > 사용자 메모리 > 프로젝트 메모리 > 관리형 정책

### 자동 메모리
`CLAUDE.md` 사용 외에도 클로드 코드는 `settings.json`에서 `autoMemoryEnabled: true`일 때 자동 메모리가 활성화된다.
이는 세션 중 학습한 내용을 기반으로 주로 사용자가 선호하거나 자주 사용하는 방식 등을 자동으로 저장하는 메모리 기능이다.

자동 메모리는 `MEMORY.md` 파일에 저장되며 사용자가 직접 편집하거나, 클로드 코드에게 **"이것을 기억해 줘"** 라고 요청하면 추가되기도 한다.

### 메모리 지침 파일의 재귀적 특성
클로드 코드는 지침 파일을 **재귀적으로 읽는 특징**을 가진다. `CLAUDE.md` 파일 안에 `@ 기호`와 함께 파일 경로를 기술하면 클로드 코드가 해당 파일의 내용을 읽어 컨텍스트에 병합한다.

다만 이러한 지침들을 효과적으로 사용하기 위해서는 다음과 같은 작성 원칙을 따라야 한다.
1. 구체적으로 작성.
2. 구조를 사용하여 구성.
3. 주기적으로 검토하며 수정.

### 재귀적 가져오기와 깊이 제한
연속적으로 `@ 구문`을 사용하여 지침 파일의 참조의 참조가 가능하나 순환 참조 방지와 메모리 로드 시간을 유지하기 위해 **4단계의 참조만을 허용**한다.

이러한 재귀 구조는 최상위 `CLAUDE.md`는 프로젝트의 핵심 규칙만을 담고, 각 규칙이 참조하는 상세 문서는 별도 파일로 분리하여 문서의 계층적 구성에 유용하다.

> TIP!
>
> `/memory` 명령을 통해 메모리 파일 위치를 확인하고 열람·편집할 수 있다. 현재 세션에 실제로 로드된 파일과 가져오기 체인을 확인하려면 `/context`를 사용한다.
> `/init` 명령어로 현 프로젝트의 코드를 분석하여 적절한 `CLAUDE.md` 파일을 생성할 수 있다.
>
> 메모리 파일에 코드 예시를 포함하는 경우가 많으므로 코드 문법에 등장하는 `@ 기호`가 가져오기로 오인되면 예기치 않은 파일 로드나 오류가 발생할 수 있다.
> 이를 방지하기 위해 `@ 참조`가 가져오기로 해석되지 않는 마크다운 코드 스팬(인라인 코드)과 코드 블록을 활용한다.

### 모듈화 전략
단일 파일에 모든 정보가 담길 경우 유지보수가 어렵고 컨텍스트 관리도 비효율적이기 때문에 프로젝트가 커질수록 메모리를 모듈화 해야 한다.

#### 핵심-참조 분리
`CLAUDE.md`는 핵심 지침과 최소한의 규칙만을 작성하고 상세한 지침은 별도 파일로 두어 `@ 구문`으로 참조한다.

#### 설정 파일 직접 참조
프로젝트의 설정 파일을 직접 참조하여 설정이 변경될 때 메모리 파일을 별도로 업데이트할 필요가 없다.

#### 도메인별 분리
도메인별로 지침 파일을 분리하고 `CLAUDE.md`에서 각 도메인의 진입점만 참조한다.

하지만 가져오기 방식이 절대적으로 좋은 방식은 아니다. 과도하게 사용할 경우 컨텍스트 윈도우가 빠르게 소모될 수 있으므로 가져오기 체인의 복잡도를 주기적으로 관리해줘야 한다.

> 가져오기 구조는 가능한 한 얕고 명확하게 유지하는 것이 장기적으로 유지보수에 유리

### 모듈형 룰 시스템
앞선 모듈화 전략에서 가져오기 방식이 절대적으로 좋은 방식이 아님을 명시하며 문제점을 지적했는데 이러한 문제를 해결할 수 있는 방법이 **모듈형 룰 시스템**이다.

`@ 구문`은 정리의 목적이지 컨텍스트 절감의 효과를 가져오지 않고 로드 시점에는 전체가 컨텍스트에 포함된다. 반면 룰 시스템은 `.claude/rules/`의 paths frontmatter는 매칭되는 파일을 열 때만 조건부로 로드되어 실제로 컨텍스트를 아낄 수 있다.

> paths 필드가 없는 룰 파일은 모든 작업에서 항상 로드된다.

### CLAUDE.md vs rules
`CLAUDE.md`와 `rules`은 상호 보완적인 관계이다. `CLAUDE.md`가 프로젝트의 핵심 아이덴티티와 고수준 지침을 받는 진입점이라면, `rules`는 세부적인 실행 규칙을 모듈화하여 관리하는 확장 메커니즘이다.

따라서, `CLAUDE.md`에는 항상 필요한 최소한의 정보를 담고, `rules`는 상세하고 조건부로 적용되는 규칙을 배치하여 컨텍스트 윈도우 소모를 절약할 수 있으며 유지보수성도 보완할 수 있다.

## 메모리 최적화와 장기 작업 관리
메모리가 비효율적으로 구성될 경우 컨텍스트 윈도우 낭비, 응답 지연, 일관성 손실의 문제점이 발생할 수 있다. 따라서 메모리에 저장할 정보를 선택할 때에는 토큰 효율성을 고려해야 한다.

- 토큰 효율성 : 특정 정보를 메모리에 저장하는 일이 매번 프롬프트로 전달하는 것보다 효율적인지 판단하는것.

### ROI(Return On Investment) 계산법
1. 해당 정보가 세션당 평균 몇 번 참조되는 지 추정
2. 메모리에 저장하면 소모되는 토큰 수와 프롬프트로 매번 전달하면 소모되는 토큰 수를 각각 계산
3. 두 값을 비교하여 메모리 저장 여부 결정

### 동적 메모리 로딩 패턴
클로드 코드에 특정 작업 시작 시 `@ 구문`과 함께 관련 메모리를 활성화하도록 요청하는 동적 메모리 로딩 패턴은 작업별로 필요한 정보만 컨텍스트에 로드하여 토큰을 절약할 수 있다.

### 메모리 파일 성숙도 모델
1. 부트스트랩 메모리: `/init` 실행 > 기본 프로젝트 정보 > 빌드 명령어
2. 경험 기반 메모리: 자주 쓰느 패턴 > 반복 지침 > 팀 규칙
3. 최적화된 메모리: 정기 검토 > 불필요한 정보 제거 > 그룹화 및 정리

### 실전 메모리 압축 기법
메모리 파일이 커지면 압축 기법을 통해 정보를 잃지 않고 토큰을 절약할 수 있다.

1. 핵심 정보 추출 기법: 간결한 지침으로 변환
2. 참조 링크 활용 기법: 상세한 문서는 외부에, 메모리에서는 링크만 유지
3. 조건부 세부 사항 기법: 일반 규칙은 메모리에, 예외 사항을 별도 파일에 저장
