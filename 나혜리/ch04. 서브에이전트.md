# 4. 서브에이전트

## 학습 목표
- 서브에이전트
- 오케스트레이터-워커 패턴

---
## 서브에이전트란?
클로드 코드의 Agent 도구를 기반으로 호출되는 특화된 AI 어시스턴트로, 자체 컨텍스트 윈도우, 커스텀 시스템 프롬프트, 할당된 도구를 가지고 있다.

스킬과 마찬가지로 서브에이전트도 YAML 프른토 매터와 마크다운으로 구성되며 마크다운 본문이 서브에이전트의 시스템 프롬프트이다.

### 오케스트레이터-워커 패턴
서브에이전트는 단순히 메인 컨텍스트 윈도우를 침범하지 않고 격리된 상태에서 일을 위임받아 작업한다 생각하지만
실제 단일 클로드 코드 인스턴스(서브에이전트 사용 x)의 작업 방식과는 근본적으로 다르다. 

#### 비교: 단일 인스턴스로 작업 vs 서브에이전트에 위임

| 항목 | 단일 인스턴스로 작업할 때 | 서브에이전트에 위임할 때 |
|---|---|---|
| 컨텍스트 윈도우 | 메인 대화 하나만 사용 | 서브에이전트가 별도의 독립된 컨텍스트 윈도우 사용 |
| 시스템 프롬프트 | 메인 인스턴스의 프롬프트 그대로 적용 | 서브에이전트마다 커스텀 시스템 프롬프트 설정 가능 |
| 도구 접근 | 메인 인스턴스가 가진 도구 전체 사용 | 서브에이전트에 필요한 도구만 제한적으로 부여 가능 |
| 중간 작업(파일 읽기, 검색 등) | 메인 컨텍스트에 그대로 누적됨 | 서브에이전트 컨텍스트 안에서만 발생, 메인에는 노출 안 됨 |
| 메인 컨텍스트에 남는 것 | 모든 중간 과정 + 결과 | 서브에이전트가 반환한 요약 결과만 |

#### 서브에이전트의 오케스트레이터-워커 패턴
서브에이전트 시스템은 **오케스트레이터-워커 패턴**을 따르며 오케스트레이터 역할인 메인 에이전트의 명령하에 서브에이전트는 워커 역할을 부여받게 된다.
마치 마이크로서비스 구조와 유사하며, 메인 에이전트는 시니어 역할을 서브에이전트는 주니어 역할을 맡게 된다.

![오케스트레이터-워커 패턴.png](image/%EC%98%A4%EC%BC%80%EC%8A%A4%ED%8A%B8%EB%A0%88%EC%9D%B4%ED%84%B0-%EC%9B%8C%EC%BB%A4%20%ED%8C%A8%ED%84%B4.png)

이렇게 각 작업과 역할을 부여받은 서브에이전트는 각 영역에서 전문성을 발휘하며 오케스트레이터의 핵심인 작업 분배와 결과 통합을 이룬다.

> **주의 사항**
> 
> 서브에이전트는 **단일 책임 원칙**을 적용해야 한다. 하나의 서브에이전트는 하나의 명확한 책임만을 가져야 동작 에측이 가능해지고 문제 발생 시 원인 파악이 쉬워진다.

### 서브에이전트를 사용해야 하는 기준
- 작업의 복잡도
- 컨텍스트 소모량
- 전문성 요구 수준

---
> **질문**: 그럼 스킬을 자동으로 찾아 호출했던 것처럼 서브에이전트도 메인에서 호출하는걸까?

**클로드의 답변**

네, 맞아요. 스킬과 비슷한 방식으로 동작해요.

- 서브에이전트를 정의할 때 `description` 필드에 "언제 사용해야 하는지"를 적어두면, 메인 인스턴스가 사용자 요청을 보고 그 설명과 매칭해서 **자동으로** Agent 도구를 호출해 서브에이전트에 위임해요.
- 예를 들어 `description: "MUST BE USED for 코드 리뷰 작업"`처럼 써두면, 사용자가 코드 리뷰를 요청했을 때 메인이 자동으로 해당 서브에이전트를 호출함.
- 물론 사용자가 프롬프트에서 서브에이전트 이름을 직접 언급하면 명시적으로도 호출 가능해요.

차이점은, 스킬은 메인 인스턴스 자체의 컨텍스트 안에서 로드되어 지식/지침이 추가되는 방식이고, 
서브에이전트는 별도의 컨텍스트 윈도우를 가진 독립된 실행 단위를 호출하는 방식이라는 점이에요. 둘 다 "자동 판단 후 호출"이라는 트리거 메커니즘은 비슷하지만, 
실행되는 위치와 격리 수준이 다릅니다.

---

### 컨텍스트 엔지니어링 원칙
모델에 제공하는 컨텍스트를 체계적으로 설계하는 방법론으로, 서브에이전트를 효과적으로 활용할 수 있도록 도와준다.

#### 적정 고도(right altitude)
서브에이전트에게 지시할 때 지침의 구체성 수준을 뜻하며, 판단에 필요한 핵심 기준은 명확히 주면서도 모든 예외 케이스까지 나열하지 않는 균형점을 찾아야 한다.

- 너무 상세하면(고도가 너무 낮으면): 모든 케이스를 일일이 명시하려다 지침이 길어지고, 핵심 목표가 세부 규칙들 사이에 묻혀서 오히려 놓치게 됨
- 너무 모호하면(고도가 너무 높으면): 방향만 던져주고 세부 기준이 없어서, 서브에이전트가 상황을 잘못 판단하고 틀린 결정을 내림

#### 컨텍스트 엔지니어링의 2가지 원칙
1. 초기 컨텍스트 설계: 전체 코드가 아닌 변경된 파일과 관련 의존성만 전달한도록 한다.
2. 작업 중 수집하는 컨텍스트 관리: 필요한 정보만 선택적으로 수집하도록 지침을 제공한다. 

#### 컨텍스트 격리의 이점
서브에이전트의 가장 큰 장점은 메인과 격리된 컨텍스트를 사용한다는 점이다. 

서브에이전트는 각 독립적인 20만 토큰 컨텍스트를 가지게 되는데 이를 활용하여 메인 대화에서는 높은 수준의 계획과 조율만 담당하고, 실제 분석이나 코드 생성은 서브에이전트에게 위임한다.

---
> **질문**: 그럼 실질적으로 스킬을 호출하는 주체는 서브에이전트가 되는건가?

**클로드의 답변**

아니요, 스킬 호출 주체가 서브에이전트로 고정되는 건 아니에요.

스킬은 어느 컨텍스트 윈도우에서 실행되든 그 안에서 자동 매칭돼요. 즉:

메인 인스턴스가 직접 작업을 처리하는 중이면, 메인 인스턴스가 스킬을 호출함
메인이 서브에이전트에게 작업을 위임했으면, 그 서브에이전트의 컨텍스트 안에서 서브에이전트가 스킬을 호출함

**핵심은 "누가 지금 그 작업을 실행 중인가"** 예요. 스킬의 description은 현재 활성화된 컨텍스트(메인이든 서브에이전트든)에서 항상 매칭 대상이 되기 때문에, 서브에이전트에 위임된 상황이면 자연스럽게 서브에이전트가 스킬을 호출하는 것처럼 보이는 거지, 스킬 호출이 서브에이전트만의 전용 기능은 아니에요.

정리하면: 스킬 호출 = 메인이든 서브에이전트든, 현재 그 태스크를 실행하고 있는 인스턴스가 수행.

---
## 서브에이전트 사용
서브에이전트는 스킬과 마찬가지로 프론트매터의 `description`필드를 통해 적절한 에이전트가 자동으로 선택되거나 명시적으로 특정 에이전트를 호출할 수 있다.

또한, 서브에이전트는 고유한 `agentId`가 할당되며 호출할 때마다 새 인스턴스로 시작하는 서브에이전트를 `agentId`를 사용하여 새 인스턴스가 아닌 지난 작업을 재개할 수 있다.

> 작업 재개가 왜 필요하지?
> 
> 해당 기능을 활용하면 복잡한 분석 작업을 단계별로 수행할 수 있다. 서브에이전트가 분석 기능을 가지고 있다면 코드 분석 후 문제 분석에 이어 개선 방안을 도출한다.

### 서브에이전트 우선순위
1. 프로젝트 에이전트
2. 사용자 에이전트
3. 기본 내장 에이전트(Built-in Agents)

### 에이전트 결과 통합
여러 개의 서브에이전트가 한 작업 안에서 실행될 경우 여러 에이전트의 결과를 통합하여 종합적인 결론을 도출한다. 이때 정보의 우선순위를 고려하여야 적절한 결론을 도출할 수 있다.

### 서브에이전트 성능 측정
서브에이전트는 작업 완료 시간, 결과의 품질과 컨텍스트 사용량을 위해 성능 지표를 활용해야 한다. 

서브에이전트를 실행 시 완료 후 에이전트의 측정 지표를 보고해달라고 요청할 수 있으며 구체적인 지시를 이용하면 더욱 구체적인 성능 데이터를 얻을 수 있다.

## 서브에이전트 정의 파일 구조
스킬과 달리 서브에이전트는 파일명이 에이전트의 고유 식별자가 된다.

**서브에이전트의 필드**

| 필드                | 필수 | 설명                                 | 예시                             |
| ----------------- |:--:|------------------------------------| ------------------------------ |
| `name`            | O  | 고유 식별자(소문자, 하이픈)                   | `code-reviewer`                |
| `description`     | O  | 에이전트 목적 설명                         | 코드 품질 전문가                      |
| `tools`           | X  | 에이전트가 사용할 수 있는 도구(쉼표로 구분)          | `Read`, `Grep`, `Glob`, `Bash` |
| `model`           | X  | 에이전트가 사용할 모델 지정                    |`sonnet`, `opus`, `haiku`, `inherit`|
| `skills`          | X  | 주입할 스킬 목록                          | `moai-core`, `moai-lang`       |
| `disallowedTools` | X  | 에이전트가 사용할 수 없는, 금지 도구(`tools`와 택일) | `Edit`, `Write`                |
| `permissionMode`  | X  | 권한 동작 모드                           | `acceptEdits`                  |
| `hooks`           | X  | 에이전트 스코프 생애 주기 훅                   | `PreToolUse`, `PostToolUse`    |
| `memory`          | X  | 영속 메모리 스코프                         | `user`, `project`, `local`     |

### permissionMode: 권한 동작 모드
에이전트의 신뢰 수준과 작업 특성에 따라 결정한다.

| 모드                  | 동작                    | 적합한 용도           |
|---------------------| --------------------- | ---------------- |
| `default`(기본값)      | 표준 권한 확인(사용자에게 승인 요청) | 범용 에이전트          |
| `acceptEdits`       | 파일 편집 작업을 자동 승인       | 신뢰할 수 있는 구현 에이전트 |
| `dontAsk`           | 모든 권한 요청을 자동 거부       | 엄격한 샌드박스 에이전트    |
| `bypassPermissions` | 모든 권한 확인을 건너뜀         | 완전 자동화 파이프라인     |
| `plan`              | 읽기 전용 모드(쓰기 작업 차단)    | 연구 및 분석 에이전트     |

> **참고** permissionMode 선택가이드
> 
> ![선택가이드.png](image/%EC%84%A0%ED%83%9D%EA%B0%80%EC%9D%B4%EB%93%9C.png)

### hooks: 생애 주기 훅
에이전트 실행 전과 후, 또는 작업이 종료되는 시점에 셸 명령을 자동으로 실행하는 매커니즘이며 해당 훅은 서브에이전트 내에서만 동작하며 전역 훅과는 독립적으로 작동한다.

### memory: 영속 메모리
에이전트 세션 간에 학습한 내용을 유지하는 기능으로 user(전역 개인용, 권장 및 기본값), project(프로젝트용), local(프로젝트 한정 개인 메모)로 범위를 나눠 사용할 수 있다

### skills
`skills`을 사용해 서브에이전트에 스킬을 제공하여 특정 도메인에 대한 전문성을 부여할 수 있다. 스킬의 작성순서대로 우선순위가 주어지므로 입력에 주의해야 한다.

> **작성 순서 팁**
> 
> 일반 규칙 먼저, 특수 규칙은 나중에
> 프로젝트 특화 규칙은 마지막에 배치

스킬을 조합하면 당연하게도 컨텍스트가 증가한다. **토큰 효율성**을 고려해 필요한 스킬을 선별하여 일관된 기준에 따라 지정해야 한다.

#### 스킬 조합 방식
기본적으로 스킬은 기반, 도메인 스킬을 함께 사용하며 에이전트의 특정 역할에 필요한 스킬만 선별하여 조합하는 방식을 **역할 특화 조합 방식**이라 한다.
- 기반 스킬: 공통 규칙과 원칙을 제공
- 도메인 스킬: 특정 분야의 지식 제공

#### 출력 포맷 지정
에이전트 결과의 일관성과 활용도를 높이기 위해 출력 형식을 명시한다.

#### 경계 조건 명시
에이저트라 처리하지 않아야 할 상황을 명확하게 정의하여 에이전트가 자신의 역할 범위를 넘어서는 동작을 방지한다. 경계 조건은 긍정적 명시와 부정적 명시를 모두 포함한다.

### 에이전트 테스트와 최적화
- 정상 케이스: 설계된 목정에 맞게 동작하는지 확인
- 경계 케이스: 예상치 못한 형식의 입력 등을 테스트
- 실패 케이스: 에이전트가 처리할 수 없는 상황에서 적절하게 대응하는지 확인

다양한 시나리오를 통해 에이전트의 동작을 검증하고 결과의 품질을 평가한다.

- 최적화: 프롬프트 다듬기, 도구 권한 조정, 스킬 조합 변경, 모델 변경 등

## 에이전트 팀
팀 기반 병렬 개발 프레임워크로 여러 에이전트(클로드 코드 인스턴스)를 하나의 팀으로 묶어 동작한다. 실제 소프트웨어 개발팀의 구조를 모델링하여 리더와 팀원으로 나뉘어 작업을 수행한다.

여기서 중요한 점은 팀원이 **영속적**이라는 점이다. 세션이 끝나면 재개를 요청하지 않는 이상 재시작을 해야 하는 서브에이전트와는 달리 
에이전트 팀의 팀원은 팀이 해산될 때까지 자신의 컨텍스트를 유지하며 여러 태스크를 연속으로 수행할 수 있다. 또한 팀원의 종료는 팀 리더의 종료 요청에만 종료할 수 있다.

### 팀 생성과 생애 주기 관리

#### 에이전트 팀 시작하기
1. 사용자가 팀 생성을 명시적으로 요청
2. 클로드 판단 하에 팀 생성을 사용자에게 제안

이렇게 생성된 팀의 팀원은 독립된 컨텍스트 윈도우를 가지나 리더의 권한 설정을 그대로 상속 받기 때문에 생성 이후에 필요에 따라 권한 설정을 변경해야 한다.

#### 에이전트 팀 아키텍처 구성 요소
1. 팀 리더: 팀원을 생성하고 작업을 조율하는 메인 Claude Code 세션
2. 팀원: 할당된 작업에서 각각 작동하는 별도의 Claude Code 인스턴스
3. 태스크 목록: 	팀원들이 요청하고 완료하는 공유 작업 항목
4. 메일박스: 에이전트 간 통신을 위한 메시징 시스템

### 메세지 전달 시스템
팀원들은 **메일박스**를 통해 정보를 공유한다.
- **자동 메시지 전달**: 팀원들이 메시지를 보낼 때, 자동으로 수신자에게 전달되며. 리더가 업데이트를 폴링할 필요가 없다.
- **유휴 알림**: 팀원이 완료되고 중지되면, 자동으로 리더에게 알린다. 턴이 API 오류로 끝난 팀원은 정상적으로 완료된 것처럼 보이는 대신 실패했음을 리더에게 알리고 오류 텍스트를 포함한다.
- **공유 작업 목록**: 모든 에이전트는 작업 상태를 보고 사용 가능한 작업을 요청할 수 있다.
- **팀원 메시징**: 
  - message: 개인 쪽지
  - broadcast: 전체 쪽지

리더는 팀원을 생성할 때 각 팀원에게 이름을 할당하며, 모든 팀원은 그 이름으로 다른 팀원에게 메시지를 보낼 수 있다. 
나중의 프롬프트에서 참조할 수 있는 예측 가능한 이름을 얻으려면, 생성 지시에서 각 팀원을 무엇이라고 부를지 리더에게 말한다.
