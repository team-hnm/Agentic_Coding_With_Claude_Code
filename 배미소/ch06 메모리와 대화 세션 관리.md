# 메모리 시스템 이해하기

## 네 가지 계층적 메모리

- 관리형 정책
    - 시스템 경로에 위치하며 조직 전체에 적용
        - macOS: `/Library/Application Support/ClaudeCode/CLAUDE.md`
        - Linux / WSL: `/etc/claude-code/CLAUDE.md`
        - Windows: `C:\Program Files\ClaudeCode\CLAUDE.md`
    - 보안 정책, 코드 표준 등 전사적 규칙을 정의
- 프로젝트 메모리
    - 프로젝트 루트의 `./CLAUDE.md` 파일에 저장
    - 프로젝트별 코딩 스타일, 아키텍처, 빌드 명령어 등을 문서화하여 팀과 공유
    - 하위 디렉터리에도 `CLAUDE.md` 를 둘 수 있으며, 해당 디렉터리의 파일을 클로드가 읽을 때 관련 `CLAUDE.md` 가 로드됨
- 사용자 메모리
    - `~/.claude/CLAUDE.md` 파일에 저장
    - 개인의 모든 프로젝트에 적용되는 기본 설정
    - 개발자 본인의 코딩 스타일, 도구 사용 방식, 개인적인 워크플로 등을 정의
- 프로젝트 로컬 메모리
    - `./CLAUDE.local.md` 파일에 저장
    - 현재 프로젝트에만 개인적으로 적용되는 설정
    - 개인이 선호하는 테스트 데이터, 로컬 개발 환경 설정 등을 정의
    - 일반적으로 Git에 커밋하지 않도록 `.gitignore`에 추가

> 관리형 → 사용자 → 프로젝트 → 로컬 순서로 로드되며 더 구체적인 위치의 내용이 나중에 컨텍스트에 들어온다.
> 
> 충돌하는 지침이 있는 경우, Claude가 임의로 하나를 선택할 수 있으므로 명시적으로 충돌을 피하는 것이 중요하다.

## 자동 메모리

- 클로드가 세션 중 발견한 유용한 정보와 패턴을 자동으로 저장하는 기능
    - 빌드 방식, 선호하는 코딩 패턴, 자주 사용하는 테스트 명령어 등
- 자동 메모리는 기본적으로 활성화되어 있으며, 필요시 `/memory`에서 끄거나 `autoMemoryEnabled: false`로 비활성화할 수 있다
- 자동 메모리는 프로젝트별로 `~/.claude/projects/<project-hash>/MEMORY.md` 에 저장된다.
    - `MEMORY.md`가 메모리의 진입점 역할을 하며, 세션 시작 시 첫 200줄 또는 25KB까지 로드된다.
    - `MEMORY.md`에 연결된 상세 메모리 파일은 필요할 때 읽는다.
    - 사용자가 직접 메모리 파일을 수정하거나 삭제할 수 있다.

## CLAUDE.md 가져오기와 조건부 로딩

- `CLAUDE.md` 파일에서 `@path/to/import` 구문으로 다른 파일을 가져올 수 있다.
- 가져온 파일 내부에서도 `@` 를 사용해 추가 파일을 가져올 수 있다.
- 최대 4단계 깊이로 다른 파일을 재귀적으로 가져올 수 있다.
- 최상위 `CLAUDE.md` 에는 핵심 규칙을 두고, 상세 내용을 별도 파일로 분리하여 활용할 수 있다.
- 마크다운 인라인 코드와 코드 블록 내부의 `@`는 import로 처리되지 않는다.

## 메모리 시스템 다루기

- `/memory` : `CLAUDE.md` 목록 확인·편집
- `/init` : 프로젝트를 분석하여 초기 `CLAUDE.md` 생성 (이미 파일이 있는 경우 개선 방향 제안)

## 모듈형 룰 시스템

- 클로드 코드는 `.claude/rules/` 디렉터리를 이용해 프로젝트 규칙을 여러 파일로 나눌 수 있다.
- 프로젝트 지침을 주제별, 도메인별로 독립된 Markdown 파일로 분리하고, 각 파일의 적용 조건을 프론트메터로 명시한다.
    - `paths` 필드 사용 시 특정 파일에만 적용할 수 있다. (없으면 매 세션 로드)

        ```yaml
        ---
        paths:
          - "src/api/**/*.ts"
        ---
        ```


### CLAUDE.md와 Rules, Skill의 핵심 차이

| 측면 | CLAUDE.md | `.claude/rules/` | Skill |
| --- | --- | --- | --- |
| 로드 | 세션 시작 | 항상 또는 경로 일치 시 | 호출되거나 관련성이 있을 때 |
| 범위 | 프로젝트/사용자/조직 | 전체 또는 특정 파일 경로 | 특정 작업 |
| 핵심 용도 | 핵심 규칙, 아키텍처, 명령어 | 조건부·세부 규칙 | 반복 가능한 작업/워크플로 |

# 체크포인팅과 복구 시스템

## `/rewind` 화면 되감기

- `/rewind`를 실행하거나 프롬프트 입력이 비어 있을 때 `Esc`를 두 번 눌러 rewind 메뉴를 열 수 있다.
- 클로드 코드는 작업 과정에서 파일 변경과 대화 상태를 체크포인트로 관리한다.
- 30일 후에 세션과 함께 자동으로 정리된다 (구성 가능)
- `/rewind`에서 특정 시점으로 돌아가 코드와 대화를 복원하거나, 코드 또는 대화만 복원하는 등의 작업을 할 수 있다.

## 체크포인팅의 제한 사항과 대응 전략

- Claude의 편집 도구를 거치지 않은 변경은 체크포인트로 복원되지 않을 수 있다.
- 따라서 중요한 변경을 영구적으로 관리하려면 Git을 함께 사용하는 것이 좋다.
    - 자동 커밋을 사용한다면 Hooks를 활용하여 Git에 별도의 복구 지점을 남기는 전략 사용 가능

## 체크포인팅과 깃

- **Checkpoint**: 클로드 작업 중 잘못된 변경을 빠르게 되돌리는 안전망
- **Git**: 프로젝트의 변경 이력을 영구적으로 관리하는 버전 관리 시스템

# 세션 관리 전략

## 세션 복구

- `claude -c`
    - 현재 디렉터리에서 가장 최근 대화 계속
    - 세션이 끊겼을 때 유용하다.
- `claude -r "<session>"`
    - 특정 세션을 ID 또는 이름으로 재개
    - 여러 작업을 병렬로 진행할 경우 유용하다.
- `/rewind`
    - 현재 세션에서 특정 체크포인트로 되돌림

## 다중 세션 관리

- 기능 개발, 버그 수정, 코드 리뷰처럼 성격이 다른 작업은 별도 세션으로 분리하면 컨텍스트가 섞이는 것을 줄일 수 있다.
- 서로 독립적인 작업은 별도 세션에서 진행한다.
- 이전 세션의 분석 결과를 파일이나 문서로 남겨두면 새로운 세션에서도 해당 결과를 다시 활용할 수 있다.
